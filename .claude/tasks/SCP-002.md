## Description

`CLAUDE.md` §6 makes checkout idempotent and requires the result to be stored.
The `idempotency_records` table exists (Phase 01) but nothing uses it. This task
turns it into a working mechanism in `app/Shared/`: an `Idempotency-Key`
middleware and an application service that wraps an operation, using the unique
index on `(scope, key)` as the race guard (insert, then handle the unique
violation; never check-then-write).

It is an enabler that must land before the Order module
(`docs/specifications/system-analysis.md` §2). Order creation and payment
confirmation are the first consumers, but neither exists yet, so this task is
proven against a test-only route and a test-only operation, not against Order.

Three behaviours the plan must decide and document (the request asks for them
to be recorded; deciding them is `/plan`'s job, not this record's):

1. Which responses are stored for replay.
2. Which outcomes release the key so a real retry can run again.
3. What happens when the process dies between claiming the key and finishing.

The criteria below hold whatever the plan decides; AC9 to AC11 require the
decisions to be written down and tested.

## Acceptance Criteria

Relevant invariant, `CLAUDE.md` §6: "Checkout must be **idempotent**; require
an idempotency key for order creation and persist its result."

And, for payment confirmation, `CLAUDE.md` §6: "Manual confirmation records
`confirmed_by`, `confirmed_at`, amount, optional bank transaction
reference/evidence metadata, and an audit event; make confirmation idempotent
and transactional."

Tests run against PostgreSQL, not SQLite (`CLAUDE.md` §12).

- [ ] **AC1 — Replay.** Two sequential requests with the same key and the same
      body, to a test route that increments a counter, return identical status
      and body, the counter is 1, and the second response carries a header
      documented to mark it as a replay.
- [ ] **AC2 — Race.** N concurrent requests (N >= 10, separate DB connections or
      processes, not sequential calls) with the same key and body execute the
      handler exactly once: counter is 1 and `idempotency_records` holds exactly
      one row for that `(scope, key)`. Every caller receives either the stored
      response or a documented "in progress" conflict; none receives a 5xx.
- [ ] **AC3 — Race mechanism.** The claim is an INSERT that relies on the
      `(scope, key)` unique index and handles the unique violation. A test or
      static check shows no SELECT-then-INSERT claim path exists. The unique
      index itself is unchanged and no migration re-creates the table.
- [ ] **AC4 — Key reuse with different input.** Same key, same scope, different
      request body returns HTTP 409 with `error.code` = `IDEMPOTENCY_KEY_REUSED`
      (already in `ErrorCode`), the handler does not run, and the stored
      response is not altered.
- [ ] **AC5 — Missing or malformed key.** On a route declared as requiring a key,
      a request without `Idempotency-Key`, with an empty one, or with one longer
      than 255 characters is rejected before the handler runs, using the
      existing error envelope and a code from `ErrorCode`. Whether the status is
      400 or 422 is the plan's call; the test asserts the documented one. The
      handler count is 0.
- [ ] **AC6 — Request hash.** `request_hash` is computed over a canonical form,
      so JSON key order and insignificant whitespace do not change it and a
      differing value does. Unit test with at least: reordered keys (same hash),
      changed value (different hash), different HTTP method or path (different
      hash). The hash fits the `varchar(128)` column.
- [ ] **AC7 — Isolation.** The same key used under a different scope, and the
      same key used under a different store context, each execute the handler
      independently. A response stored for one store is never replayed to a
      request in another. Test with two stores and one shared key value.
- [ ] **AC8 — Database invariants hold.** Every row the code writes satisfies
      `idempotency_records_status_valid` and
      `idempotency_records_completed_has_response`. A `COMPLETED` row always has
      a non-null `response_status`. Verified by running the AC1, AC2, AC4 and
      AC9 to AC11 scenarios and asserting no constraint violation was raised or
      swallowed.
- [ ] **AC9 — Stored versus released, decided and tested.** The plan's decision
      on which responses are stored and which release the key is written in a
      table in `docs/api/README.md` (Headers section) covering at least: 2xx,
      4xx validation failure, 409 business conflict, 5xx / uncaught exception.
      For each row there is a test asserting the key's state afterwards
      (`COMPLETED` with replay, or key released and a retry executes the handler
      again). No row is left undecided.
- [ ] **AC10 — Handler failure.** When the handler throws, the record is never
      left `COMPLETED` with a success status, and a transaction opened by the
      handler is rolled back. The disposition documented under AC9 for this case
      is what a following retry observes.
- [ ] **AC11 — Process death, decided and tested.** A test simulates death
      between claiming the key and storing the result (record left
      `IN_PROGRESS`, handler never completed). A retry arriving before the
      documented recovery point gets the documented "in progress" response and
      the handler does not run twice concurrently; a retry after it follows the
      documented recovery rule. The recovery time bound is configuration, named
      in `.env.example` and `config/`, with no business-policy default
      hard-coded.
- [ ] **AC12 — Expiry.** `expires_at` is set on every row from configuration. A
      request whose key matches only an expired record is treated as a new
      request and the handler runs. A scheduled or invokable cleanup removes
      expired rows; a test shows a row past `expires_at` is deleted and an
      unexpired one is not.
- [ ] **AC13 — Atomicity with the wrapped operation.** For an operation that
      writes business rows, either both the business rows and the `COMPLETED`
      record are committed or neither is. A test that forces failure after the
      handler's writes and before commit leaves no business rows and no
      `COMPLETED` record.
- [ ] **AC14 — No sensitive data in logs.** Log lines emitted by the mechanism
      contain the request id, scope and outcome, and do not contain the request
      body or the stored `response_body`. Asserted by capturing log output in
      the replay, conflict and failure tests.
- [ ] **AC15 — Architecture.** All new code lives under `app/Shared/`; domain-layer
      code added does not reference Eloquent, facades or HTTP; the existing
      `tests/Unit/ArchitectureTest.php` passes unmodified. If the plan finds it
      cannot, this task is split before implementation rather than widened.
- [ ] **AC16 — Contract.** `docs/api/openapi.json` (the committed file; the
      workflow docs mention `.yaml`, which does not exist in the repository)
      documents the `Idempotency-Key` header, the replay indicator and the 409
      responses. CI's OpenAPI reproducibility check passes.
- [ ] **AC17 — Quality gates.** Pint, PHPStan/Larastan and the full Pest suite
      pass, including all previously existing tests.

### 2. The defects, confirmed by reading

**D1 — AC6: the hash is of the raw body, so key order changes it.**
`EnsureIdempotency::fingerprint()` hashes
`method | path | user id | $request->getContent()`, and `getContent()` is the
raw bytes. Two consequences, both real:

- A client that re-serialises its payload on retry in a different key order —
  a different platform, a different JSON library, a map iterated twice — gets
  409 `IDEMPOTENCY_KEY_REUSED` for an honest retry of the same operation. That
  is the exact failure the mechanism exists to prevent, inverted. AC6 requires
  reordered keys to hash the same.
- The query string is excluded by a deliberate comment ("a retry may
  legitimately carry a new trace id"). That discards a *distinguishing* input:
  two different requests to the same path differing only in query hash
  identically, and the second is answered with the first one's stored response.
  AC6 does not demand the query be included; correctness does.

The existing tests cannot catch this because the helper `fingerprintFor()`
reproduces the production expression, including `json_encode($body)` in the
test's own key order. A test that reimplements the implementation cannot
falsify it.

Fix: a pure `RequestFingerprint` in `Shared/Domain/Idempotency/` that
canonicalises — decode JSON, recursively sort object keys (array *element*
order stays significant), re-encode with fixed flags; sort the query string;
include method and path; keep the actor id. A non-JSON or undecodable body
hashes raw, which is correct and must be stated. sha256 hex is 64 characters,
inside `varchar(128)`.

**D2 — AC7: nothing carries the store.** The scope is exactly the route's
middleware argument (`idempotent:order.create`); the store appears in neither
the scope nor the hash. In a host-resolved multi-store deployment one route
serves every store, so a key used in store A and then in store B collides. With
identical bodies the second request is answered with store A's stored response
— a cross-store data leak. With differing bodies it is a 409, so the handler
still does not run for store B. AC7 fails either way.

Fix, and the direction matters: the store must go in the **scope**, not the
hash. In the hash, store B would get 409 `IDEMPOTENCY_KEY_REUSED`; AC7 requires
the handler to *execute independently*. So `scope = "<operation>:<store_id>"`,
or `"<operation>:-"` when the route declares itself global
(`idempotent:meta.ping,global`). A store-scoped operation with no resolved
store throws a developer-facing `LogicException`, so a route that forgets
`store.resolve` fails loudly instead of silently sharing one global namespace.
Sizing: `scope` is `varchar(100)`; the longest designed operation name
(`payment.bank-account.update`, 27 chars) plus `:` plus a 36-char UUID is 64.
The middleware validates the operation argument at ≤ 63 characters, so the
column cannot overflow. No schema change, and the value stays readable to an
operator — the withdrawn plan hashed the scope only because it also folded the
actor in, which the request hash already covers.

**D3 — AC12: the lookup ignores `expires_at`.** `resolveExisting()` reads the
row and replays or 409s whatever its age. An expired record is neutralised only
when the hourly prune happens to remove it, so "expired" means "expired plus up
to an hour", and a key matching an expired `COMPLETED` row replays a day-old
response instead of running the handler.

Fix: on a unique violation, if the row is past `expires_at`, reclaim it —
conditional `DELETE ... WHERE id = ? AND expires_at <= now()`, then retry the
claim once (at most twice in total, then 409 `REQUEST_IN_PROGRESS` rather than
looping). The affected-row count is the decision, so two concurrent reclaimers
cannot both win.

**D4 — AC13/AC10: the completing write is a second commit.** `run()` calls
`$operation()` and only after it returns — after the handler's own
`DB::transaction()` has committed — does it `save()` the `COMPLETED` record. A
crash or a failure in between leaves business rows committed with no record:
the retry re-runs and creates a second order. This is the one unmet criterion
that is a correctness defect rather than a missing test.

Fix: one `DB::transaction()` around `$operation()` **and** the completing
`UPDATE`. A handler's own `DB::transaction()` nests as a savepoint inside it, so
the guard's transaction remains the real boundary. §6.

**D5 — AC11/AC14: no recovery bound, and no logging.** Process death leaves
`IN_PROGRESS`, and with D3 fixed the row answers 409 until `expires_at` — a
recovery bound of 24 hours expressed as a retention setting. That is a bad
client contract: "retry the same key with backoff" would be a lie for a day.
Fix: one new config key, `in_progress_timeout_seconds` (§7), plus a fence so a
reclaim cannot be overwritten by a zombie process. And one structured log line
per outcome, carrying no body and no `response_body`.

### 3. The one decision that is the Tech Lead's (AC9)

The approved AC9 decision was: 409 business conflicts **stored**; other 4xx and
all 5xx **release** the key. The shipped code's docblock says the opposite —
"anything below 500 is stored and replayed, including client errors".

Reading the code, neither description is what actually happens. Disposition
depends on *how* the outcome arrives:

- the handler **returns** a response → `status >= 500` releases, anything else
  is stored;
- the handler **throws** → `catch (Throwable)` deletes the record and rethrows,
  i.e. releases, whatever the status would have been.

Whether a thrown `BusinessRuleViolation(OutOfStock)` reaches that `catch` at all
depends on `Illuminate\Routing\Pipeline`, which renders exceptions raised by
the pipes and by the destination into responses inside the pipeline. If it
renders before returning to `$next()`, a 409 conflict is *stored*; if it
propagates, the same 409 is *released*. The repository's own tests cannot
distinguish the two, because the only thrown-handler test asserts a 500 and 500
releases on both paths. `vendor/` is not installed on this machine, so I did
not verify which it is; the implementer must read
`vendor/laravel/framework/src/Illuminate/Routing/Pipeline.php` on the pinned
13.x before writing the map.

Either way the shipped behaviour is **undefined by status**, and that is a
defect independent of which policy is chosen: the guard must decide from the
resolved HTTP status so that a 422 behaves identically whether it was thrown or
returned. Mechanically: `catch (Throwable $e)`, resolve a status from it
(`BusinessRuleViolation::$errorCode->httpStatus()`,
`HttpExceptionInterface::getStatusCode()`, `ValidationException` → 422, else
500), apply the same map as the returned path, then rethrow.

| Outcome | Option A — the approved AC9 | Option B — the code's stated intent |
| --- | --- | --- |
| 2xx | stored, replayed | stored, replayed |
| 409 business conflict | stored, replayed | stored, replayed |
| 400 / 422, 401 / 403, 404, 429 | released, T2 rolled back | stored, replayed |
| 5xx / uncaught | released, T2 rolled back | released, T2 rolled back |

The consequence that decides it, for a real client. Under **B**, a client sends
a bad payload, gets 422, fixes the payload and retries with the same key: the
hash now differs, so it gets a hard 409 `IDEMPOTENCY_KEY_REUSED` for the rest
of the retention window. Keys are commonly minted once per checkout attempt and
reused across user corrections, so a typo becomes a dead checkout until the
client is clever enough to mint a new key. Under **A**, that retry simply runs,
and releasing is safe precisely because nothing happened.

What A costs: the answer to a key is no longer final for those statuses, and
"released" has to mean the operation's writes are rolled back as well —
otherwise a handler that wrote rows and then returned 404 would duplicate them
on retry. So under A a wrapped handler cannot persist anything on a released
outcome; anything it must keep (a failed-attempt audit row) has to be written
outside the guard, or that outcome has to be stored. That constraint must be
documented for consumers.

**Recommendation: Option A**, with release defined as "T2 rolls back and the
claim row is deleted". It is what the approved criteria say, the Tech Lead has
not revised them, and a client stuck on its own typo is a worse failure on a
flaky mobile network than non-finality for statuses where no business decision
was reached. **This needs Tech Lead approval before implementation**: it changes
observable behaviour of a mechanism already on `main`. The only code difference
between A and B is the status→disposition map and the rollback rule, and the
tests in §9 are written one per row of the chosen table, so switching costs four
test expectations.

Two sub-decisions that are *not* the Tech Lead's, recorded for the table:
"released" is a row delete rather than `status = 'FAILED'` (so `FAILED` stays an
unused constant permitted by the CHECK — harmless, noted so nobody "fixes" it);
and a replayed error envelope keeps the *original* `request_id`, `timestamp` and
`path` while the response's own `X-Request-Id` header is the current request's.
That asymmetry goes in the README so no integrator correlates the wrong request.

### 6. Transaction boundaries

Three transactions, in order. The split is the correctness argument.

**T1 — the claim, alone, committed before the operation starts.** A single
INSERT. It must be visible to a concurrent retry, otherwise the unique index
never collides and the race guard is decorative. The existing nested
`DB::transaction()` around it stays, for the SAVEPOINT reason in the current
docblock. Consequence to enforce: the guard asserts `transactionLevel() === 0`
on entry and throws a `LogicException` otherwise — being called from inside
someone else's transaction would make the claim invisible until that commits.

**T2 — one `DB::transaction()` containing everything that must be atomic**
(the D4 fix):

1. the wrapped operation's writes — order rows, `order_status_history`, stock
   decrements taken under `lockForUpdate()` *by the operation*, and any
   `outbox_events` row the flow records;
2. the `UPDATE ... SET status='COMPLETED', response_status=?, response_body=?
   WHERE id = <my row> AND status='IN_PROGRESS'`.

**Which outbox events are written inside it: none by the guard.** Nothing
business-meaningful happens when a key is claimed or replayed, so there is no
event to publish. The inverse is what matters: the guard opening T2 is what
makes a consumer's `DatabaseOutbox::record()` legal — it refuses to write
outside a transaction (`transactionLevel() === 0` → `RuntimeException`) — and it
is what puts the consumer's outbox row and the `COMPLETED` record in one commit,
as `CLAUDE.md` §6 requires.

**Row locks taken by the guard: none.** Serialisation is the unique index plus
affected-row counts on conditional statements, never read-then-write. The only
lock it relies on is the implicit row lock PostgreSQL takes on the conditional
`DELETE` during a reclaim, which makes two concurrent reclaimers serialise so
exactly one sees `1 row`.

If the completing UPDATE reports **0 rows**, this process has lost its claim
(its row was reclaimed while it ran): it throws, T2 rolls back, the operation's
writes vanish, and the caller gets 409 `REQUEST_IN_PROGRESS` with a
`lost_claim` warning logged. That is the fence, and it needs no schema, because
a reclaim is `DELETE` + `INSERT` and therefore changes the row id.

**T3 — disposition, after T2 has rolled back**, as its own short statement,
applying the §3 table: delete the claim row (released) or write the `COMPLETED`
409 envelope (stored business conflict). Conditional on
`id = <my row> AND status='IN_PROGRESS'`, so a row someone else already
reclaimed is never clobbered. T3 cannot be inside T2 — a rolled-back
transaction cannot record why it rolled back.

**Process death** anywhere between T1's commit and T2's commit leaves
`IN_PROGRESS` and *no* business state, because T2 is all-or-nothing. Recovery:
within `in_progress_timeout_seconds` of `updated_at` → 409
`REQUEST_IN_PROGRESS`; after it → the conditional reclaim `DELETE`, a fresh
claim, and the handler runs. Recovery is by timeout, not by the scheduler: a
client retrying 30 seconds later must not wait for an hourly tick, and
`CLAUDE.md` §16 permits only one scheduler coordinator, so that tick is a single
point of delay. The pruner's job stays retention.

**Consumer constraint, to be documented** (§4): a wrapped operation must keep
its side effects inside T2. An inline HTTP call to a bank or a notification
provider is not covered by the rollback and would be duplicated by a retry;
those go through `outbox_events`, which T2 does cover.

### 7. Idempotency, concurrency and configuration

**What the key covers.** `(scope, key)` where
`scope = "<operation>:<store_id|->"`, and the stored `request_hash` covers
method, path, canonical query, canonical JSON body and the authenticated actor
id. Same scope + same key + same hash → the stored outcome. Same scope + same
key + different hash → 409 `IDEMPOTENCY_KEY_REUSED`. A different store or a
different operation → independent execution. A different actor reusing the same
key value in the same store → the hash differs, so 409 rather than a
cross-actor replay; that is the safe direction, and it is why the actor stays in
the hash and not in the scope.

**How two concurrent requests serialise.** Both INSERT; PostgreSQL's unique
index lets exactly one through and hands the other
`UniqueConstraintViolationException`; the loser then reads the row and answers
from it (replay, 409 reuse, or 409 in progress). There is no check-then-write
path anywhere. A loser whose read finds the row already gone answers 409
`REQUEST_IN_PROGRESS` rather than guessing — the shipped code already does this
and it stays.

**Configuration** — `config/commerce.php` under the existing `idempotency`
block, with matching entries in the root `.env.example` and in
`EnvironmentValidator::validateCommerce()`, which today validates
`bank_transfer.expiry_minutes` and `inventory.reservation_ttl_minutes` but
neither idempotency value:

| Key | Env | Default | Meaning |
| --- | --- | --- | --- |
| `idempotency.retention_hours` | `COMMERCE_IDEMPOTENCY_RETENTION_HOURS` | 24 (exists, already in `.env.example`) | `expires_at = created_at + this`; never extended on completion, so a key's life is measured from the first attempt |
| `idempotency.in_progress_timeout_seconds` | `COMMERCE_IDEMPOTENCY_IN_PROGRESS_TIMEOUT_SECONDS` | **new**, 120 | the AC11 recovery bound; validated as an integer ≥ 30 and documented as "must exceed the gateway and PHP-FPM request timeouts" — `infra/nginx/conf.d/fastcgi-api.inc` cuts a request well before this, so a reclaim is a safety net, not the normal path |

Both are operational bounds, not business policy: no `CLAUDE.md` §15 decision is
encoded here, which is what AC11 requires. Read through `config()`, never
`env()`, so `config:cache` is safe. `IdempotencyGuard` takes both as
constructor arguments from the existing `AppServiceProvider` binding.

A cheaper alternative the Tech Lead may prefer: declare `retention_hours` itself
the recovery bound and add no new key. It satisfies AC11 literally and is less
code, but it makes the documented client contract ("retry the same key with
backoff") false for up to 24 hours after a crash, which is why it is not the
recommendation.

**Logging (AC14).** One structured line per outcome, on top of the
`Log::withContext(['request_id' => ...])` that `AssignRequestId` already sets:
context `operation`, `store_id`, `record_id`, `outcome`, `response_status`, and
`key_digest` (the first 12 hex of sha256 of the key — the key is client-chosen
and its charset permits values that look like personal data, and a digest still
correlates the two lines of one retry). `outcome` is one of `claimed`,
`completed`, `replayed`, `released`, `conflict_key_reused`,
`conflict_in_progress`, `reclaimed_stranded`, `reclaimed_expired`,
`lost_claim`; info for the first three, warning for the rest. Never logged: the
request body, `response_body`, or the raw key.

### 8. Authorization

**No new permission code, and `RolePermissionSeeder` is untouched.** Idempotency
is not an authorization decision; it is a concurrency decision taken after
authorization has passed. Both halves named, as required:

- **Permission code**: whatever the wrapped route declares. For the first real
  consumer, `store.can:payment.confirm` — `payment.confirm` is seeded in
  `database/seeders/RolePermissionSeeder.php` and granted to `CASHIER` and
  above. Order creation is customer-facing and carries no permission code.
- **Store-scope check**: `store.resolve` (`ResolveStoreContext`, which takes the
  store from the route, the host map or the single-store default, never the
  query string) plus `store.can` (`EnsureStorePermission`, membership in *that*
  store). The guard then folds the resolved store id into the scope, so the
  scope is enforced twice over: once as access, once as replay isolation
  (§2 D2).
- **Ordering, load-bearing**: `idempotent` is declared **last, innermost**:

```php
Route::post('/orders', [CreateOrderController::class, 'store'])
    ->middleware(['throttle:commerce-write', 'store.resolve', 'idempotent:order.create']);

Route::post('/admin/payments/{payment}/confirm', [ConfirmPaymentController::class, 'store'])
    ->middleware(['auth:sanctum', 'store.resolve', 'store.can:payment.confirm', 'idempotent:payment.confirm']);
```

  so a 401/403 caller never claims a key — it cannot be burned or probed by
  someone who would be rejected anyway — and the store is resolved before the
  scope is composed. This convention belongs in the `routes/api.php` header
  comment beside the existing store-scope convention.

How the store id reaches `app/Shared/`: `ResolveStoreContext` gains one line,
`$request->attributes->set('store_id', $store->id)`, and the Shared middleware
reads that primitive. The alternative — injecting
`App\Modules\Store\Application\StoreContext` into Shared code — inverts the
intended Shared ← Modules direction, and the existing `ArchitectureTest` would
not catch it, since `App\Modules` is only required `toOnlyBeUsedIn('App')`. The
one-line edit is outside `app/Shared/`, which AC15 constrains; it is an edit to
existing code rather than new code, and **the reviewer should confirm that
reading of AC15** rather than have it surface in review.

Concurrency (AC2) — **new `tests/Concurrency/` suite**, because
`RefreshDatabase` wraps each test in a transaction and genuine cross-connection
concurrency cannot be observed inside one. Registered as a third `<testsuite>`
in `phpunit.xml` so `vendor/bin/pest --ci` picks it up unchanged, and bound in
`tests/Pest.php` to `TestCase` *without* `RefreshDatabase`.

Mechanism, and it is honestly runnable in this repository: the parent takes a
PostgreSQL advisory lock, then spawns N = 10 children with
`Symfony\Component\Process\Process` running a script in
`tests/Support/concurrency/`; each child boots `bootstrap/app.php`, registers
the same test route, blocks on the same advisory lock, then dispatches one
`POST` through the HTTP kernel with the same key and body. The parent releases
the lock and all ten proceed. Each child is a separate OS process with its own
PDO connection, which is exactly what AC2 asks for and what a sequential loop
cannot provide. Two facts make it work here: the CI `php-tests` job exports
`DB_*` in the job environment, so children inherit the same
`smart_commerce_test` database; and `AppServiceProvider` skips
`EnvironmentValidator` for the console SAPI, so a child boots without extra
configuration. Assertions: exactly one fresh 2xx; exactly one `audit_logs` row;
exactly one `idempotency_records` row for that `(scope, key)`, `COMPLETED`;
every other child got a replayed 2xx or 409 `REQUEST_IN_PROGRESS`; **no child
got a 5xx**.

Two honesty conditions. The suite commits rows outside any test transaction, so
it must clean up what it created explicitly (scope-keyed deletes in
`afterEach`) or it leaks into other suites. And if the children cannot be
spawned the test **fails** — it must not skip. A skipped concurrency test is
exactly the false gate `docs/workflow/quality-gates.md` exists to prevent.

A second, cheaper and fully deterministic test complements it rather than
replacing it: on two separate Laravel connections, hold an uncommitted claim on
connection A and issue the same INSERT on connection B with a short
`lock_timeout`, asserting that B blocks on the unique index rather than
inserting a duplicate. It proves the index really serialises. It does not
satisfy AC2 on its own and is not offered as if it did.

Gates (AC17), none of which could be run here: `pnpm api:pint:check`,
`pnpm api:stan`, `pnpm api:test`, `pnpm api:openapi` plus the CI diff (expected:
no diff), `pnpm openapi:conformance` (expected: still 2 of 2 conforming),
`pnpm format:check`.

| # | Risk | What makes it real | What catches it |
| --- | --- | --- | --- |
| 1 | Wrapping `$next()` in T2 holds a transaction for the whole handler, including response serialisation, so a slow handler holds locks longer | a checkout that does anything slow inside the handler | the §6 consumer constraint (no external calls inside T2), documented in the README; the p95 order-write budget in `CLAUDE.md` §10; a reviewer check that no wrapped handler performs I/O. | 2 | Opening T2 in the guard silently satisfies `DatabaseOutbox`'s "must be inside a transaction" check for every wrapped consumer, weakening that guard | a future Order action relying on the guard's transaction instead of declaring its own | the outbox's own test still asserts the level-0 refusal; state it in the README as "the guard provides the transaction", not "the rule went away" |

| 4 | A handler slower than `in_progress_timeout_seconds` is reclaimed and runs twice | a legitimately slow checkout, or the timeout set below the request timeout | the fence (§6): the first process's completing UPDATE affects 0 rows and T2 rolls back; the validator floor of 30s; the zombie-fence test. | 5 | Canonicalising the body changes the hash of every record already stored | a deploy while records from the old scheme are live | nothing in production uses the middleware yet (no route carries `idempotent`) and records expire within `retention_hours`, so the window is empty today; if that changes, deploy against an empty table or accept one retention window of 409s, and say which |

| 9 | `ErrorCode` and `packages/api-contracts/src/errors.ts` can drift; nothing in CI compares them | no drift from this task, which adds no code | noted only: a CI check comparing the two is a small separate task, not this one |
