## Description

`CLAUDE.md` §6 makes checkout idempotent and requires the result to be stored.
The `idempotency_records` table exists (Phase 01) but nothing uses it. This task
turns it into a working mechanism in `app/Shared/`: an `Idempotency-Key`
middleware and an application service that wraps an operation, using the unique
index on `(scope, key)` as the race guard (insert, then handle the unique
violation; never check-then-write).

It is an enabler that must land before the Order module
(`docs/specifications/system-analysis.md` §2). Order creation and payment
confirmation are the first consumers, but neither exists yet, so this task is
proven against a test-only route and a test-only operation, not against Order.

Three behaviours the plan must decide and document (the request asks for them
to be recorded; deciding them is `/plan`'s job, not this record's):

1. Which responses are stored for replay.
2. Which outcomes release the key so a real retry can run again.
3. What happens when the process dies between claiming the key and finishing.

The criteria below hold whatever the plan decides; AC9 to AC11 require the
decisions to be written down and tested.

- none. This task is backend-only and, per the request, belongs entirely in

## Acceptance Criteria

Relevant invariant, `CLAUDE.md` §6: "Checkout must be **idempotent**; require
an idempotency key for order creation and persist its result."

And, for payment confirmation, `CLAUDE.md` §6: "Manual confirmation records
`confirmed_by`, `confirmed_at`, amount, optional bank transaction
reference/evidence metadata, and an audit event; make confirmation idempotent
and transactional."

Tests run against PostgreSQL, not SQLite (`CLAUDE.md` §12).

- [ ] **AC1 — Replay.** Two sequential requests with the same key and the same
      body, to a test route that increments a counter, return identical status
      and body, the counter is 1, and the second response carries a header
      documented to mark it as a replay.
- [ ] **AC2 — Race.** N concurrent requests (N >= 10, separate DB connections or
      processes, not sequential calls) with the same key and body execute the
      handler exactly once: counter is 1 and `idempotency_records` holds exactly
      one row for that `(scope, key)`. Every caller receives either the stored
      response or a documented "in progress" conflict; none receives a 5xx.
- [ ] **AC3 — Race mechanism.** The claim is an INSERT that relies on the
      `(scope, key)` unique index and handles the unique violation. A test or
      static check shows no SELECT-then-INSERT claim path exists. The unique
      index itself is unchanged and no migration re-creates the table.
- [ ] **AC4 — Key reuse with different input.** Same key, same scope, different
      request body returns HTTP 409 with `error.code` = `IDEMPOTENCY_KEY_REUSED`
      (already in `ErrorCode`), the handler does not run, and the stored
      response is not altered.
- [ ] **AC5 — Missing or malformed key.** On a route declared as requiring a key,
      a request without `Idempotency-Key`, with an empty one, or with one longer
      than 255 characters is rejected before the handler runs, using the
      existing error envelope and a code from `ErrorCode`. Whether the status is
      400 or 422 is the plan's call; the test asserts the documented one. The
      handler count is 0.
- [ ] **AC6 — Request hash.** `request_hash` is computed over a canonical form,
      so JSON key order and insignificant whitespace do not change it and a
      differing value does. Unit test with at least: reordered keys (same hash),
      changed value (different hash), different HTTP method or path (different
      hash). The hash fits the `varchar(128)` column.
- [ ] **AC7 — Isolation.** The same key used under a different scope, and the
      same key used under a different store context, each execute the handler
      independently. A response stored for one store is never replayed to a
      request in another. Test with two stores and one shared key value.
- [ ] **AC8 — Database invariants hold.** Every row the code writes satisfies
      `idempotency_records_status_valid` and
      `idempotency_records_completed_has_response`. A `COMPLETED` row always has
      a non-null `response_status`. Verified by running the AC1, AC2, AC4 and
      AC9 to AC11 scenarios and asserting no constraint violation was raised or
      swallowed.
- [ ] **AC9 — Stored versus released, decided and tested.** The plan's decision
      on which responses are stored and which release the key is written in a
      table in `docs/api/README.md` (Headers section) covering at least: 2xx,
      4xx validation failure, 409 business conflict, 5xx / uncaught exception.
      For each row there is a test asserting the key's state afterwards
      (`COMPLETED` with replay, or key released and a retry executes the handler
      again). No row is left undecided.
- [ ] **AC10 — Handler failure.** When the handler throws, the record is never
      left `COMPLETED` with a success status, and a transaction opened by the
      handler is rolled back. The disposition documented under AC9 for this case
      is what a following retry observes.
- [ ] **AC11 — Process death, decided and tested.** A test simulates death
      between claiming the key and storing the result (record left
      `IN_PROGRESS`, handler never completed). A retry arriving before the
      documented recovery point gets the documented "in progress" response and
      the handler does not run twice concurrently; a retry after it follows the
      documented recovery rule. The recovery time bound is configuration, named
      in `.env.example` and `config/`, with no business-policy default
      hard-coded.
- [ ] **AC12 — Expiry.** `expires_at` is set on every row from configuration. A
      request whose key matches only an expired record is treated as a new
      request and the handler runs. A scheduled or invokable cleanup removes
      expired rows; a test shows a row past `expires_at` is deleted and an
      unexpired one is not.
- [ ] **AC13 — Atomicity with the wrapped operation.** For an operation that
      writes business rows, either both the business rows and the `COMPLETED`
      record are committed or neither is. A test that forces failure after the
      handler's writes and before commit leaves no business rows and no
      `COMPLETED` record.
- [ ] **AC14 — No sensitive data in logs.** Log lines emitted by the mechanism
      contain the request id, scope and outcome, and do not contain the request
      body or the stored `response_body`. Asserted by capturing log output in
      the replay, conflict and failure tests.
- [ ] **AC15 — Architecture.** All new code lives under `app/Shared/`; domain-layer
      code added does not reference Eloquent, facades or HTTP; the existing
      `tests/Unit/ArchitectureTest.php` passes unmodified. If the plan finds it
      cannot, this task is split before implementation rather than widened.
- [ ] **AC16 — Contract.** `docs/api/openapi.json` (the committed file; the
      workflow docs mention `.yaml`, which does not exist in the repository)
      documents the `Idempotency-Key` header, the replay indicator and the 409
      responses. CI's OpenAPI reproducibility check passes.
- [ ] **AC17 — Quality gates.** Pint, PHPStan/Larastan and the full Pest suite
      pass, including all previously existing tests.

## Technical Plan

### 0. The three decisions, up front

| # | Decision | Answer |
| --- | --- | --- |
| 1 | Which responses are stored, which release the key | 2xx **stored**; 409 business conflict **stored**; 4xx request/caller failures (400, 401, 403, 404, 422, 429) **released**; 5xx and uncaught exceptions **released**. Full table in §5. |
| 2 | Process death between claim and result | The claim row is left `IN_PROGRESS`. A retry inside `commerce.idempotency.in_progress_timeout_seconds` gets 409 `IDEMPOTENCY_IN_PROGRESS`; a retry after it **reclaims by timeout** (atomic conditional `DELETE` then `INSERT`), so recovery never waits for the scheduler. The cleanup job only enforces retention (`expires_at`), it is not the recovery path. The new row id is the fence token that stops a woken-up zombie process from committing. §6. |
| 3 | Scope composition | `scope = "<operation>:" + substr(sha256(store_id ‖ "|" ‖ actor_type ‖ "|" ‖ actor_id), 0, 32)`, built by one pure function so Auth (#10) changes the actor component and nothing else. §4. |

No open `CLAUDE.md` §15 decision blocks this task. Retention, the in-progress
timeout and the response-size cap are operational configuration, not business
policy. Guest identity (§15) changes how strong the actor component is for
unauthenticated callers; §4 keeps that as one named seam and states the
consumer rule that holds until #10 lands, rather than inventing an identity
policy here.

### 2. API contract

#### Request header

`Idempotency-Key` — required on every route carrying the `idempotent`
middleware. 1–255 characters, `[A-Za-z0-9._:-]`. Clients must use a fresh
unguessable value per logical operation (a UUIDv4 or v7).

#### Response header

`Idempotent-Replayed: true` — present **only** on a replayed response. Absent
means the handler executed. Named after the de-facto convention; the IETF draft
standardises only the request header, so no standard response header exists to
follow. Nothing else about the first response is reproduced: an idempotent
operation must therefore not depend on `Location` or any other response header
to carry its result — the result belongs in the body. (Our API already
identifies created resources in the body, so this costs nothing.)

#### Error codes

Two cases added to `App\Shared\Presentation\Http\ErrorCode`. **This is a public
contract change and is the main reason Tech Lead approval is required.**

| Code | Status | When |
| --- | --- | --- |
| `IDEMPOTENCY_KEY_REQUIRED` | **400** | header missing, empty, > 255 chars, or illegal characters |
| `IDEMPOTENCY_IN_PROGRESS` | **409** | the first attempt for this `(scope, key)` is still running, or is stranded and not yet past the recovery bound |

`IDEMPOTENCY_KEY_REUSED` already exists (409) and is used unchanged.

400 rather than 422 for a missing key, deliberately: `docs/api/README.md` maps
400 to a malformed request and 422 to a request that parsed but is semantically
invalid, with per-field `details`. A header problem has no field to name, and
`INVALID_STORE_CONTEXT` — the other "context, not content" failure — is already
400. AC5 lets the plan choose; the tests assert 400.

The same two codes must be added to `packages/api-contracts/src/errors.ts`
(`ERROR_CODE`) in the same change. That file is the web apps' copy of this list
and silently drifts otherwise; nothing in CI compares them today (noted in §11
risk 2).

#### OpenAPI

**`docs/api/openapi.yaml` does not exist and must not be created.** The
repository's contract document is `docs/api/openapi.json`, generated from the
code by `dedoc/scramble` via `pnpm api:openapi`
(`infra/scripts/export-openapi.sh`) and diffed by the CI step "OpenAPI document
is current". Hand-editing it fails that step. The plan therefore specifies what
the **generated** document must end up containing, and how the generator is
made to produce it.

Mechanism: register two Scramble transformers in `AppServiceProvider::boot()`.

1. A **document transformer** that adds, unconditionally and
   environment-independently (so the output is reproducible between a developer
   container and CI):
   - `components.parameters.IdempotencyKey` — `in: header`, `required: true`,
     `schema: {type: string, maxLength: 255, pattern: "^[A-Za-z0-9._:-]{1,255}$"}`,
     with a description covering replay and the recovery bound;
   - `components.headers.IdempotentReplayed` — `schema: {type: string, enum: ["true"]}`;
   - `components.responses.IdempotencyKeyRequired` (400),
     `components.responses.IdempotencyKeyReused` (409),
     `components.responses.IdempotencyInProgress` (409) — each with the error
     envelope inlined and the `code` pinned by example. The envelope is inlined
     rather than extracted into a shared `ErrorEnvelope` schema: that extraction
     is a document-wide change and belongs in its own task.
2. An **operation transformer** that, for any documented route whose middleware
   list contains the `idempotent` alias, attaches `$ref`s to the
   `IdempotencyKey` parameter, the three error responses, and the
   `Idempotent-Replayed` header on the operation's 2xx response.

Today the operation transformer matches nothing — the mechanism is proven on a
test-only route that is **not** registered in the application (§8), so no probe
endpoint leaks into a production route table and the document stays truthful.
AC16 is satisfied by the components, which document the header, the replay
indicator and both 409s. When `POST /api/v1/orders` lands with
`idempotent:order.create`, its operation is annotated automatically and cannot
drift from the code — which is the whole argument for a generated document.

Implementation note: Scramble is pre-1.0 (`^0.13.53`) and its extension API has
moved between minors. Before writing, check `vendor/dedoc/scramble` for
`Scramble::configure()->withDocumentTransformers()` /
`withOperationTransformers()` and fall back to the version's actual hook.
Verify that unreferenced components survive generation; if they are pruned, the
fallback is to reference them from the document's `info.description` plus an
`x-` extension, and that fallback needs recording here before it is used.

#### `docs/api/README.md`

- Headers table: correct the `Idempotency-Key` row (it currently says "Required
  on order creation") to "Required on any endpoint documented as idempotent",
  and add an `Idempotent-Replayed` row.
- New subsection **"Idempotency"** under Headers carrying the AC9 table from §5

  `IDEMPOTENCY_IN_PROGRESS`, retry the same key with backoff; the eventual

  semantically equal JSON, not byte-identical (see §5).
- Status-code table: 400 row gains "or a missing/malformed `Idempotency-Key`".

### 3. Database

**No migration. No schema change.** The existing table already carries every
column this design needs, and AC3 forbids re-creating it:

| Need | Existing column / constraint |
| --- | --- |
| race guard | `unique (scope, key)` from `2026_11_09_000400_create_platform_tables.php` |
| same-input check | `request_hash varchar(128)` — sha256 hex is 64 chars, fits with room |
| lifecycle | `status varchar(20)` + `idempotency_records_status_valid` CHECK (`IN_PROGRESS`, `COMPLETED`, `FAILED`) |
| replayable result | `response_status int null`, `response_body jsonb null` + `idempotency_records_completed_has_response` CHECK |
| retention and expiry | `expires_at timestamptz` + its index, which is exactly the pruner's predicate |
| staleness clock for recovery | `updated_at` from `timestampsTz()` |

Deliberately **not** added, with reasons:

- a `store_id` / `actor_id` column — the scope digest carries both, and adding
  them would mean changing the unique index, i.e. re-creating the constraint
  AC3 pins;
- a `locked_until` or `claim_token` column — `updated_at` plus the configured
  timeout gives the recovery bound, and the row id of a freshly inserted claim
  gives the fence token (§6), so neither needs schema;
- a `response_headers` column — only the replay marker is reproduced and it is
  derived, see §2;
- a test-only counter table — the test handler writes `audit_logs` rows
  (`store_id`, `actor_id`, `request_id` are all nullable there), so "the counter
  is 1" is a row count in a real table and AC13's "business rows" are real rows.
  No fixture schema, no migration, nothing to clean up beyond the suite's own
  database reset.

`FAILED` is used, not left dead: it is the released state (§5). The schema's
author put it in the CHECK; this is what it is for.

Statement shapes (all through the query builder except the one noted):

```
claim      INSERT INTO idempotency_records (id, scope, key, request_hash, status, expires_at, created_at, updated_at)
           VALUES (…, 'IN_PROGRESS', now() + retention, …)      -- unique violation = collision
reclaim    DELETE FROM idempotency_records
           WHERE scope = ? AND key = ?
             AND (expires_at <= now()
                  OR status = 'FAILED'
                  OR (status = 'IN_PROGRESS' AND updated_at < now() - interval))   -- 1 row = I won
complete   UPDATE … SET status='COMPLETED', response_status=?, response_body=?, updated_at=now()
           WHERE id = ? AND status = 'IN_PROGRESS'              -- 0 rows = I lost the claim
release    UPDATE … SET status='FAILED', response_status=?, updated_at=now()
           WHERE id = ? AND status = 'IN_PROGRESS'
prune      DELETE FROM idempotency_records
           WHERE id IN (SELECT id FROM idempotency_records WHERE expires_at < now() LIMIT :batch)
```

The pruner's `IN (SELECT … LIMIT …)` is the one place raw-ish SQL is used,
justified under `CLAUDE.md` §7 as a bounded atomic delete: an unbounded
`DELETE` on a hot table holds locks for as long as the backlog is large.

**Lookup decision matrix** on a unique violation, where `R` is the existing row.
Evaluated in this order:

| `R` | Request hash | Outcome |
| --- | --- | --- |
| `expires_at <= now()` (any status) | any | reclaim, handler runs (AC12) |
| `COMPLETED` | matches | replay stored status + body, `Idempotent-Replayed: true` |
| `COMPLETED` | differs | 409 `IDEMPOTENCY_KEY_REUSED`, nothing mutated (AC4) |
| `FAILED` | any | reclaim with the new hash, handler runs — nothing was stored or done, so the key is not bound to a body |
| `IN_PROGRESS`, `updated_at` within the timeout | matches | 409 `IDEMPOTENCY_IN_PROGRESS` |
| `IN_PROGRESS`, `updated_at` within the timeout | differs | 409 `IDEMPOTENCY_KEY_REUSED` |
| `IN_PROGRESS`, `updated_at` past the timeout | any | attempt reclaim; won → handler runs, lost → 409 `IDEMPOTENCY_IN_PROGRESS` |

The claim path for an unseen key is **only** the INSERT — there is no
`SELECT` before it (AC3). A `SELECT` happens only after the unique violation has
already told us a row exists, and every state change after that is a conditional
`DELETE` or `UPDATE` whose affected-row count is the decision, never a read
followed by a write. A reclaim that loses its INSERT race retries the whole
sequence at most twice, then returns 409 `IDEMPOTENCY_IN_PROGRESS` rather than
looping.

### 4. Scope composition (decision 3, AC7)

```
operation   "order.create"            declared on the route: idempotent:order.create
context     store_id | actor_type | actor_id
scope       operation . ":" . substr(sha256(context), 0, 32)
```

- `operation` is an `OperationName`: lower-case, dot-separated, ≤ 64 chars,
  validated at construction. This fixes the migration comment's convention
  (`order.create`) as the rule: `<module>.<verb>`, e.g. `order.create`,
  `payment.confirm`, `payment.bank-account.update`.
- `store_id` is the resolved store's UUID, or the literal `-` for a route
  explicitly declared global.
- `actor_type|actor_id` today: `user|<uuid>` when `$request->user()` is present
  (Sanctum already works — `GET /api/v1/me` uses it), `guest|-` otherwise,
  `system|-` for a non-HTTP caller. When Auth (#10) lands it changes this one
  function and nothing else; when guest identity is decided (§15) a guest token
  becomes `guest|<sha256 of the token>` by the same composition.

Why a digest rather than the readable tuple: `scope` is `varchar(100)`, and
`order.create` + two UUIDs + separators does not fit — and widening the column
means re-creating the unique index, which AC3 forbids. The digest is
fixed-length, keeps the btree small, and keeps identifiers that may be personal
data (a future guest token) out of a column that appears in operator queries.
The cost is that operators cannot grep the table by store; mitigated because the
operation name stays in clear text in the column and the structured log line
carries `store_id` and the operation separately (§7).

Route declaration, and the ordering that makes AC7 true:

```php
Route::post('/orders', [CreateOrderController::class, 'store'])
    ->middleware(['throttle:commerce-write', 'store.resolve', 'idempotent:order.create']);

Route::post('/admin/payments/{payment}/confirm', [ConfirmPaymentController::class, 'store'])
    ->middleware(['auth:sanctum', 'store.resolve', 'store.can:payment.confirm', 'idempotent:payment.confirm']);
```

`idempotent` is **innermost, always last**. Two consequences, both
load-bearing: an unauthenticated or unauthorized caller never claims a key (so
a key cannot be burned or probed by someone who would be rejected anyway), and
the store context is already resolved when the scope is composed. A route that
needs no store declares it explicitly — `idempotent:order.create,global`;
otherwise the middleware throws a developer-facing `LogicException` when store
context is unresolved, so a route missing `store.resolve` fails loudly in
development instead of silently sharing one global scope across stores.

### 5. Stored versus released (decision 1, AC9)

This table goes verbatim into `docs/api/README.md`, and each row has a test
(§9). "Released" means the row is marked `FAILED` and is reclaimable by the
next request with that key, immediately.

| Outcome of the wrapped operation | Record afterwards | Replayed? | A retry with the same key |
| --- | --- | --- | --- |
| **2xx** success | `COMPLETED`, `response_status` + `response_body` stored | yes, with `Idempotent-Replayed: true` | gets the stored response; handler does not run |
| **409** business conflict (`BusinessRuleViolation` whose `ErrorCode` is 409: `OUT_OF_STOCK`, `PRICE_CHANGED`, `MENU_UNAVAILABLE`, `INVALID_STATE_TRANSITION`, `PAYMENT_ALREADY_CONFIRMED`, `PAYMENT_AMOUNT_MISMATCH`) | `COMPLETED`, the 409 envelope stored | yes | gets the stored 409; handler does not run |
| **422 / 400** validation failure | `FAILED` (released), `response_status` recorded, no body | no | handler runs again |
| **401 / 403** authentication or authorization failure | `FAILED` (released) | no | handler runs again |
| **404** not found | `FAILED` (released) | no | handler runs again |
| **429** rate limited | `FAILED` (released) | no | handler runs again |
| **5xx** / uncaught exception | `FAILED` (released); the operation's transaction is rolled back | no | handler runs again |
| guard's own 409s (`IDEMPOTENCY_KEY_REUSED`, `IDEMPOTENCY_IN_PROGRESS`) | untouched | n/a | unchanged |

Reasoning, by class — they are not the same case:

- **2xx.** The point of the mechanism. `CLAUDE.md` §6: "persist its result".
- **409 business conflict — stored.** The contentious one. Releasing it would
  be safe against duplication (nothing was created), but it makes the key
  non-final: a client that showed the customer "sold out" and gave up could
  have an automatic retry still in flight which then *succeeds* and creates an
  order the customer believes failed. Storing makes the outcome of a key final
  and the client's state deterministic; a client that genuinely wants a fresh
  attempt mints a fresh key. This also matches how established payment APIs
  treat `Idempotency-Key`: the response to a key is the response to that key,
  error or not.
- **4xx request/caller failures — released.** Nothing reached a business
  decision; the failure is about the request or the caller. Burning the key
  would trap a client that fixes its payload in a permanent 409
  `IDEMPOTENCY_KEY_REUSED` — the mechanism would create an outage out of a
  typo. Releasing is safe precisely because no effect occurred.
- **5xx — released.** This is what a retry is *for*. Safe because of §6: the
  operation's writes and the `COMPLETED` row share one transaction, so a throw
  leaves no partial business state to duplicate.

Two mechanical details the table implies:

- **`jsonb` normalises.** The stored body is re-serialised by PostgreSQL, so a
  replay is **semantically equal JSON, not byte-identical** (object key order is
  not preserved). AC1's "identical body" is asserted with `assertExactJson`,
  not a string comparison. Documented in the README so no client depends on
  byte equality.
- **Empty bodies.** A 204 or any non-JSON response stores `response_status` with
  `response_body = null`; the CHECK permits it and the replay returns the same
  status with an empty body. A streamed or file response on an idempotent route
  is a design error: the guard throws `LogicException`.
- **Size cap.** Inside the transaction, before committing, the encoded body is
  measured against `commerce.idempotency.max_response_bytes` (default 65536).
  Over the cap the guard aborts the transaction and surfaces 500
  `INTERNAL_ERROR` with an error log, rather than committing a result it cannot
  faithfully replay. It is a loud bug, not silent truncation. The default is
  generous enough that a single-resource write response will never reach it; an
  endpoint that does should not be wrapped.

### 6. Transaction boundaries, crash recovery and the fence (AC10, AC11, AC13)

Three transactions, in this order. The split is the whole correctness argument.

**T1 — claim, committed immediately, on its own.** A single INSERT. It must
commit before the operation starts, otherwise a concurrent retry would not see
it and the unique index would never collide — the race guard would be
decorative. Consequence: the guard must not be invoked inside an already-open
transaction, and asserts `transactionLevel() === 0` on entry, throwing a
`LogicException` if not.

**T2 — one `DB::transaction()` containing everything that must be atomic:**

1. the wrapped operation's writes (order rows, `order_status_history`, stock
   decrements, and — once SCP's outbox dispatcher exists — the `outbox_events`
   rows written by the same flow, per `CLAUDE.md` §6);
2. the `UPDATE … SET status='COMPLETED' … WHERE id = <my row> AND status = 'IN_PROGRESS'`.

If the operation opens its own `DB::transaction()`, Laravel nests it as a
savepoint and T2 stays the real boundary — which is what AC13 needs. Either the
business rows and the `COMPLETED` record both commit, or neither does. If the
completing UPDATE reports **0 rows**, this process has lost its claim (its row
was reclaimed while it was running): it throws, T2 rolls back, the operation's
writes vanish, and the caller gets 409 `IDEMPOTENCY_IN_PROGRESS` with a
`lost_claim` warning logged.

**T3 — disposition, after T2 failed**, in its own short transaction, applying
§5: either `release` (→ `FAILED`) or `complete` with the stored 409 envelope for
a business conflict. Both are conditional on
`id = <my row> AND status = 'IN_PROGRESS'`, so a row someone else has already
reclaimed is never clobbered. T3 must not be inside T2 — a rolled-back
transaction cannot record why it rolled back.

**Process death (decision 2).** Death anywhere between T1's commit and T2's
commit leaves the row `IN_PROGRESS` and no business state, because T2 either
committed as a whole or not at all. Recovery:

- retry **within** `in_progress_timeout_seconds` of the row's `updated_at` →
  409 `IDEMPOTENCY_IN_PROGRESS`, handler does not run;
- retry **after** it → the reclaim `DELETE` above. Exactly one concurrent
  reclaimer gets `1 row` (the `DELETE` takes the row lock, so they serialise);
  it then INSERTs a fresh claim and runs the handler. Losers get 409.

**Reclaimed by timeout, not by the cleanup job**, because: (a) recovery must not
depend on a scheduler tick — a client retrying 30 seconds later would otherwise
be stuck until the next run, and `CLAUDE.md` §16 allows exactly one scheduler
coordinator, so that tick is a single point of delay; (b) the conditional
`DELETE` is the same race-safe primitive as the claim, so there is one
concurrency argument to review rather than two; (c) the cleanup job's job is
retention, and an operational window measured in minutes has nothing to do with
a retention window measured in hours.

**The fence.** Reclaim is `DELETE` + `INSERT`, not `UPDATE`, so the reclaimed
claim has a **new row id**. A stranded process that wakes up late and tries to
complete finds its own `id` gone, gets 0 affected rows, and rolls back (above).
This is why no `claim_token` column is needed: the row id *is* the token, and
the fence works without schema change. The timeout default must exceed the real
request timeout so this is a rare safety net rather than the normal path —
nginx cuts a request at `fastcgi_read_timeout 30s`
(`infra/nginx/conf.d/fastcgi-api.inc`), so the default is 120s and
`EnvironmentValidator` refuses a value below 30.

(Worth noting why this matters beyond client retries: that same nginx config
sets `fastcgi_next_upstream error timeout invalid_header`. Timeouts are retried
by the infrastructure, not only by the customer.)

### 7. Configuration, logging and the cleanup job

`config/commerce.php`, under the existing `idempotency` block (with matching
entries in `.env.example` and in `EnvironmentValidator::validateCommerce()`):

| Key | Env | Default | Meaning |
| --- | --- | --- | --- |
| `idempotency.retention_hours` | `COMMERCE_IDEMPOTENCY_RETENTION_HOURS` | 24 (exists) | `expires_at = created_at + this`; set on claim, never extended on completion, so a key's lifetime is measured from the first attempt |
| `idempotency.in_progress_timeout_seconds` | `COMMERCE_IDEMPOTENCY_IN_PROGRESS_TIMEOUT_SECONDS` | 120 | the recovery bound of decision 2; validated as an integer ≥ 30, documented as "must exceed the gateway and PHP-FPM request timeouts" |
| `idempotency.max_response_bytes` | `COMMERCE_IDEMPOTENCY_MAX_RESPONSE_BYTES` | 65536 | §5 size cap; validated ≥ 1024 |
| `idempotency.prune_batch_size` | `COMMERCE_IDEMPOTENCY_PRUNE_BATCH_SIZE` | 1000 | rows per delete statement |

These are operational bounds, not business policy, which is what AC11 requires:
no expiry window, cash policy or refund rule is encoded here, and every value is
read through `config()`, never `env()`, so it survives `config:cache`.

**Cleanup (AC12).** `idempotency:prune` deletes `expires_at < now()` in batches
until none remain, logging the total. Scheduled in `routes/console.php` —
`Schedule::command('idempotency:prune')->hourly()->withoutOverlapping()` — the
first entry in this repository's schedule; compose already runs exactly one
`schedule:work` service. Artisan only, no HTTP route: a purge endpoint is an
unauthenticated-deletion risk for no benefit.

**Logging (AC14).** One structured line per outcome, through the existing
`Log::withContext(['request_id' => …])` that `AssignRequestId` already set:

```
context: request_id, operation ("order.create"), store_id, actor_type,
         key_digest (first 12 hex of sha256(key)), record_id, outcome,
         response_status (for completed/released)
outcome: claimed | completed | replayed | released | conflict_key_reused
       | conflict_in_progress | reclaimed_stranded | lost_claim
level:   info for claimed/completed/replayed; warning for every conflict,
         reclaim and lost_claim
```

Never logged: the request body, `response_body`, or the raw key. The key is
client-chosen and its charset permits things that look like personal data
(`john.doe:2026`), so only a digest is logged — it is still enough to correlate
two log lines for the same retry.

### 8. Proving it without an Order module

No real consumer exists, so the mechanism is proven against a **test-only
route** that is registered by the tests, not by the application: no config flag,
no probe endpoint in the route table, nothing to disable in production. The
handler inserts one `audit_logs` row with `action = 'test.idempotent-handler'`
and returns JSON; "the counter" is the number of those rows.

The concurrency children (§9) boot `bootstrap/app.php` themselves and register
the same route before handling a request, so they exercise the real middleware
stack in a real separate process.

**How a real consumer opts in**, later, with no change to this code:

1. HTTP: append `idempotent:<operation>` to the route's middleware, innermost
   (§4). The Scramble operation transformer documents it automatically.
2. Non-HTTP (a queued job, an admin console command, a future AI tool per
   `CLAUDE.md` §11): call
   `IdempotencyGuard::run(IdempotencyContext, Closure): StoredOutcome`
   directly. The guard takes and returns primitives and imports no
   `Illuminate\Http`, which is what makes the same validated operation callable
   off the HTTP path (§3).

One constraint consumers inherit, and it must be in the README: an operation
wrapped by the guard must keep its side effects inside T2. An inline HTTP call
to a notification provider or a bank API inside the handler is not covered by
the rollback and would be duplicated by a retry — those go through
`outbox_events`, which T2 covers.

wraps each test in a transaction, which makes genuine cross-connection
concurrency impossible to observe. Registered as a third `<testsuite>` in
`phpunit.xml` (so `vendor/bin/pest --ci` picks it up in CI unchanged) and bound
in `tests/Pest.php` with `DatabaseTruncation` instead of `RefreshDatabase`, so
the data is actually committed and visible to other connections.

- **AC2 / AC3, real race.** The parent takes a PostgreSQL **advisory lock**
  (`pg_advisory_lock`), spawns N = 10 child processes with
  `Symfony\Component\Process\Process` (ships with Laravel) running a script
  under `tests/Support/concurrency/`, each of which boots the framework,
  registers the test route, blocks on the same advisory lock, then issues the
  same POST with the same key and body. The parent releases the lock; all ten
  proceed within microseconds. Each child is a separate OS process with its own
  PDO connection — genuinely concurrent, which is what
  `docs/workflow/quality-gates.md` demands and a sequential loop cannot provide.
  Assertions: exactly one 2xx-fresh response; exactly one `audit_logs` row;
  exactly one `idempotency_records` row for that `(scope, key)`, `COMPLETED`;
  every other child got either a replayed 2xx or 409 `IDEMPOTENCY_IN_PROGRESS`;
  **no child got a 5xx**. Children are passed `APP_ENV=testing` and the
  `*_test` database explicitly, consistent with the guard in `Tests\TestCase`.

  silently skipped concurrency test is exactly the false gate
  `docs/workflow/quality-gates.md` is about.

### 10. Authorization

The guard introduces **no permission code** and leaves `RolePermissionSeeder`
untouched. Idempotency is not an authorization decision; it is a concurrency
decision taken after authorization has already passed. The authorization-related
content of this plan is therefore entirely about ordering and scope:

- **Permission check**: whatever the wrapped route already declares
  (`store.can:payment.confirm` for the future payment-confirmation consumer).
  The guard runs after it, so a 403 never claims a key.
- **Store scope**: enforced twice over. `store.resolve` + `store.can` decide
  access, and the resolved store id is then folded into the scope digest so a
  response stored for store A can never be replayed to a request in store B
  (AC7). A route that forgets `store.resolve` fails loudly rather than
  defaulting to a shared global scope (§4).
- **Cross-actor replay** is the residual risk: the scope distinguishes
  authenticated users, but all unauthenticated callers currently share
  `guest|-`. Consumer rule, to be documented in the README and honoured by the
  Order module: an unauthenticated idempotent operation must include a
  server-issued unguessable identifier (the cart id) in its body, so a replay
  requires the exact `request_hash` and therefore knowledge of a resource the
  caller already holds. This is a mitigation, not a proof; see §11 risk 5 and
  the Security Findings expectation already recorded in this task.
