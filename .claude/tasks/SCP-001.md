## Description

When a customer chooses `BANK_TRANSFER` at checkout, the API must return a
dynamic VietQR payload they can scan in a Vietnamese banking app, together with
the receiving account details, the exact amount, and a transfer reference
unique to the order.

Scoped deliberately to **generating and displaying** the payload. Verifying
that money arrived is a separate task: `CLAUDE.md` §6 is explicit that QR
generation is not payment confirmation, and keeping the two in one task is how
that distinction gets blurred.

## Dependencies

- `Order` module — a payment belongs to an order, and neither exists yet.
  `docs/specifications/system-analysis.md` §2 puts Order before Payment.
- `store_bank_accounts` table and its admin endpoint — the payload needs a
  configured receiving account, and `PUT /admin/stores/{store}/bank-account` is
  designed in `docs/api/openapi.yaml` but not built.
- **Not blocked** by the open `CLAUDE.md` §15 decision on which bank account,
  what expiry window and what exception policy. Those are configuration and
  policy; this task reads them from store settings. Going live needs them
  answered, shipping this code does not.

## Acceptance Criteria

- [ ] **AC1** — `GET /orders/{order}/payment` on a `BANK_TRANSFER` order returns
      `qr_payload`, `transfer_reference`, `amount` and the bank's `bin`,
      `account_number`, `account_name`, matching the `BankTransferInstructions`
      schema in `docs/api/openapi.yaml`.
- [ ] **AC2** — `amount` equals the order's `total_amount` exactly, as integer
      đồng. `CLAUDE.md` §6: "Monetary arithmetic must be exact; for VND use
      `BIGINT` integer đồng or an agreed `DECIMAL`, never floating-point."
- [ ] **AC3** — The payload is a standards-compliant VietQR/EMVCo string with a
      valid CRC, and amount and reference are encoded inside it rather than
      left for the customer to type.
- [ ] **AC4** — `transfer_reference` is derived from the order code, unique per
      order, and within the character and length rules banks accept. A
      uniqueness constraint in the database makes a collision impossible rather
      than unlikely.
- [ ] **AC5** — The payment row is created with status `PENDING`. No code path
      reachable by a customer can move it to `PAID`. `CLAUDE.md` §6: "never let
      the customer self-confirm `PAID`, and never treat a screenshot, QR
      display, or 'I have transferred' click as proof of funds."
- [ ] **AC6** — Requesting the payload twice returns the same reference and the
      same payload. Regenerating on each read would hand two references to one
      order and make a bank statement unmatchable.
- [ ] **AC7** — With no bank account configured for the store, checkout refuses
      `BANK_TRANSFER` with a documented error code rather than producing a
      payload nobody can pay into.
- [ ] **AC8** — `expires_at` is set from store configuration, and the endpoint
      answers 410 after it passes. A transfer arriving later is an exception for
      staff, never an automatic reopen.
- [ ] **AC9** — A guest reads the payload only with a valid
      `X-Guest-Order-Token`; the order id alone is not enough.
- [ ] **AC10** — No bank account number, payload or reference appears in any log
      line. `CLAUDE.md` §8: redact payment details in logs.

## Technical Plan

Not yet written. Run `/plan SCP-001`.

The architect will have to settle one thing explicitly: whether the EMVCo
payload is built in this repository or by a verified library. `CLAUDE.md` §6
says to "avoid reliance on an unverified third-party endpoint", which rules out
calling someone's QR-image URL at request time, but does not decide between a
small well-tested local builder and a maintained package. That choice needs the
CRC and field encoding to be provably right, so whichever it is, it needs unit
tests against known-good payloads.
