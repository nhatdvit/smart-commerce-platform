## Description

Install the Git-driven, agent-based development workflow this directory is part
of: specialised agents, the eight workflow skills, the task ledger, review
report templates, safety hooks, workflow documentation and a traceability CI
gate.

Id `SCP-000` rather than `SCP-001` on purpose: this is the scaffolding the
numbered work runs through, not a product feature. It is also recorded here
because a workflow that exempts its own installation from its own ledger is
making a claim it does not believe.

It was installed directly rather than through `/task` → `/plan` → `/implement`,
for the obvious reason that none of those existed yet. The design was approved
as a Phase A proposal before any file was written, which is the same gate
`/plan` enforces.

## Technical Plan

Presented and approved as the Phase A proposal. In short:

- Orchestration lives in **skills**, which run in the main session, because a
  subagent cannot delegate to another subagent. An agent definition that told
  one agent to call another would simply not work, and the brief forbids
  inventing unsupported orchestration.
- Enforcement is split three ways by what each mechanism can actually do:
  skills validate state, hooks hard-block irreversible operations with
  `exit 2`, and CI gates the pull request. Merge approval belongs to GitHub and
  cannot be enforced from here.
- `settings.json` carries hooks only, no `permissions` block. Tool permissions
  are the operator's security setting, and the brief warns specifically against
  shipping permissive ones.
- The existing `ci.yml` is left alone. Its seven jobs already cover the brief's
  quality gates; adding to them would duplicate work and slow every run.

## Security Findings

Reviewed 2026-11-13 by `security-reviewer`; full report at
`.claude/reviews/SCP-000/security-review.md`. Verdict: **CHANGES REQUIRED**,
with 0 CRITICAL, 4 HIGH, 7 MEDIUM and 3 LOW, included in the consolidated

No finding is reachable by a customer. The diff adds no application code, no
endpoint, no migration and no dependency, so every payment-integrity, store
isolation and guest-token check in the report is N/A — examined and marked so
rather than ticked. The findings are all about the enforcement this change

What the reviewer cleared, and it is worth recording because it is the part
that was built right: the CI workflow uses `pull_request` rather than
`pull_request_target`, declares `permissions: contents: read`, and passes the
attacker-controlled PR title through `env:` instead of `${{ }}` inside
`run:` — so there is no script injection from a fork. Neither Node script lets
a branch-controlled string reach a shell: both use `execFileSync` with an argv
array and no `shell: true`.

On the deliberate absence of a `permissions` block in `settings.json`, the
reviewer half agrees and the disagreeing half is worth acting on. Omitting
`allow` is right for the stated reason — a committed allowlist silently widens
permissions on every machine that clones the repository. But that argument does
not reach `deny`, which can only ever remove capability, and three deny rules
over `.claude/hooks/**`, `.claude/settings.json` and `.github/workflows/**`
would turn prose into enforcement at no cost to the operator (S8, S9).
